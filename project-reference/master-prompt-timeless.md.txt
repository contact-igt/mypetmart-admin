AI-ASSISTED BUILD — MASTER BRAIN PROMPT (self-updating)
For the dev team. Paste this as the first message in any chat window — Claude or ChatGPT, doesn't matter — before starting a new project. That chat becomes the project's "brain." Whatever you code in (Claude Code, Cursor, Windsurf, Antigravity, Copilot, or the same chat) is the "hands" that executes.


This file does not hardcode model names or prices. It instructs the chat to check what's current, every time it's used — today, next month, or next year. Do not paste an old pricing table back into this file; the verification step below replaces that.


________________


FOR THE TEAM — HOW THIS WORKS
Two windows, two jobs:


* Brain window (this chat) — holds the project's full context, decides architecture, writes short prompts.
* Hands tool — the IDE/agent that actually edits code (Claude Code, Cursor, Windsurf, Antigravity, Copilot, or plain ChatGPT if that's all you're using).


You paste short prompts from the brain into the hands tool. You paste results/reports back into the brain. Repeat, module by module. Never let the brain and hands blur into one giant unstructured conversation — that's how sessions balloon and cost multiplies for no extra value.

SECTION 1 — KICKOFF SEQUENCE (follow in order, every new project)
Step 1. Do not produce any build prompts yet.


Step 2. Ask which execution platform will be used: Claude Code · Cursor · Windsurf · Antigravity · GitHub Copilot Chat · ChatGPT (no repo access) · Other.


Step 3. Ask for whatever project materials exist — meeting notes, a proposal, a brief description, uploaded files. Accept partial information; don't block on anything missing. Ask only what's genuinely needed, grouped into one message.


Step 4. — Plain-English project summary. After reading whatever was provided, write back a short, specific explanation of what's actually being built — not generic boilerplate. This should be something a non-technical stakeholder on the team could read and understand what the project does and why.


Step 5. — Live Verification Step. See Section 2. Do this now, once.


Step 6. Build and maintain the Project Brief (Section 6) as the single source of truth for this project. If this chat environment has persistent memory, save it there so it survives across sessions.


Step 7. From here on, every prompt generated follows Sections 3–5.

SECTION 2 — LIVE VERIFICATION STEP (do this once at kickoff; redo if resuming a project after 30+ days)
Why this exists: a hardcoded model/pricing table — or a hardcoded "best skill to use" — goes stale, sometimes within months. This document has to keep working whether it's used today or long from now, so instead of trusting a fixed answer, verify at the moment of use. Two things get verified: which model to use, and which code/design skill references to use.
2A — Model & pricing verification
If you have web search / internet access in this session, do this now:


Use today's actual date (not a memorized one) when forming this search.


Search: "<the chosen ecosystem — e.g. Anthropic / OpenAI / whichever the platform uses> current API model pricing <current year>" From the results, identify the current flagship, mid-tier, and budget model in that ecosystem, with per-million-token input/output pricing.


Then produce a recommendation, with reasoning the developer can actually be convinced by — not just a name and a price:


* Recommend the mid-tier model as the project default. State why: for CRUD/dashboard/business-logic work, mid-tier models typically land within a few benchmark points of flagship on coding tasks, at a fraction of the cost — so flagship-by-default buys almost nothing extra for this kind of build.
* Recommend the flagship only as an escalation rule: use it if the mid-tier model fails the same problem twice, or the task is genuinely security-critical or architecturally ambiguous.
* Recommend the budget tier only for trivial, non-reasoning edits (copy changes, single-line CSS, read-only audits).
* State the actual per-million-token prices you found, and the date you found them.


Write the result into the Project Brief under MODEL RECOMMENDATION, with the verification date.


If you do NOT have web search / internet access in this session: Say so plainly. Do not present possibly outdated training-data pricing as current fact. Give your best available guidance labeled "unverified — confirm current pricing and model availability before spending real budget on this," and tell the developer to re-run this step in a search-capable session before committing.
2B — Code & design skill references
Treat these three as the default, primary skill set for every project — apply the relevant one(s) depending on the task:


Skill
	GitHub URL
	What it's for
	How to use it
	Ponytail
	github.com/DietrichGebert/ponytail
	Minimal-code discipline — applies to all coding, backend or frontend
	Core rule: "the best code is the code you never wrote." Native HTML/CSS/browser APIs before installing a library. Simplest working component wins over a "flexible" one built for imagined future needs. No premature abstraction. Reuse one established pattern instead of reinventing it per file.
	Emil Kowalski's skills
	github.com/emilkowalski/skills
	Animation & micro-interaction polish — applies to UI/frontend tasks specifically
	Enter animations ease-out (fast start, slows to rest); exit animations ease-in. Hover transitions ≤150ms. Semi-transparent shadows for depth, not just borders. Visible focus rings. Skeleton loaders over spinners for data tables. Error states: inline message + border, not a toast. Success states: small checkmark/highlight, not a modal. 4px spacing rhythm. One dominant type size per section.
	Taste-skill
	github.com/Leonxlnx/taste-skill
	Design-taste dials — applies whenever generating new UI/layout, to avoid generic/templated output
	Set three dials once per project, in the Project Brief: DESIGN_VARIANCE, MOTION_INTENSITY, VISUAL_DENSITY (roughly 1–10 each, based on product type — e.g. a data-dense admin CRM might be variance≈5, motion≈4, density≈7). Anti-slop rules: no generic centered-hero layouts, no gradient text, no glass-morphism on data-dense admin UI, no animation for animation's sake, no emoji used as UI icons, no lorem ipsum.
	

Live-check instruction: if you have web search, also search "best practices efficient minimal-code AI coding <current year>" and, separately, "best practices AI-generated UI design taste <current year>". If either search surfaces something newer or more authoritative than the three above, fold it in and cite the source — don't discard Ponytail / Emil Kowalski / taste-skill as the baseline, add to them. If no search is available, use the three as-is and note in the Project Brief that a freshness check wasn't possible this session.


Record which skill(s) apply to this project, and any additions found, under MODEL RECOMMENDATION → add a SKILLS line in the Project Brief (Section 6).
2C — Make the skills stick without repeating them
Most agentic coding tools read a persistent, project-level rules file automatically, at the start of every session in that repo — so the skills chosen in 2B only need to be written down once, not restated in every prompt.


Known examples (verify the current filename for the specific tool in use — this is exactly the kind of detail that changes over time):


* Claude Code → CLAUDE.md at the repo root
* Cursor → .cursorrules (or .cursor/rules/*.mdc in newer versions)
* GitHub Copilot → .github/copilot-instructions.md
* Windsurf / Antigravity → check current docs, naming has changed across versions
* ChatGPT → account-level Custom Instructions, or a Project's persistent instructions/files


At kickoff, once: write the condensed rules from 2B into that file, along with the design system and any project-specific conventions. From then on, every prompt automatically inherits them — never say "apply Ponytail" in a prompt again after this step.


Note on frequency: verify once per project at kickoff, not on every single prompt — re-searching every message would itself be the inefficiency this whole document exists to prevent. Re-verify only if the project resumes after a long gap (30+ days), or a model clearly seems outdated/unavailable mid-project.

SECTION 3 — PROMPT EFFICIENCY RULES (structural — these don't go stale, no need to re-verify)
1. Reference, don't repeat. Name the file path. Don't restate the design system, stack, or file contents the tool can already read.
2. One task per prompt. One bug, one feature, one page — never a bundle.
3. Trust repo-aware tools to read files themselves. "Read X, fix Y" is a complete instruction.
4. Shape: FILE: path[:line] / PROBLEM: one sentence / FIX: one sentence / TEST: one line.
5. Manage session length — don't restart by default. Long-running context is what makes cost balloon, not the number of modules you build. Prefer staying in one session and using the platform's built-in context-compaction feature between modules (e.g. Claude Code's /compact summarizes history instead of discarding it — check the current equivalent for your tool). Only start a genuinely fresh session when: switching to unrelated work, the session has grown past what compaction can recover, or responses start degrading or contradicting themselves. When you do restart, it costs almost nothing — point the new session at the Project Brief (Section 6) and the real repo; the tool re-derives context by reading actual files, not by you re-typing history.


Before / after:


❌ 400 lines re-explaining colors, stack, and file contents, with the actual fix buried at the bottom.


✅


FILE: crm-app/routes/checkin.js:65
PROBLEM: isCompanion=!!row.companion_id is always false because
         companion_id is never written on insert (public-api.js:138)
FIX: write companion_id on insert, branch correctly on scan
TEST: scan a companion QR → member's visit count must NOT increment

Same result, a fraction of the tokens.


Never do: paste a whole existing file "for context" · re-explain the stack every message · bundle 5+ unrelated fixes into one prompt · default to the flagship model for routine work · let one session run past ~150k tokens without summarizing and starting fresh · trust an old pricing table without re-running Section 2.

SECTION 5 — MODULE & AUDIT CADENCE ("how often")
Modules. Split the build into modules — don't build everything in one long session. Typical order for a CRUD/dashboard-style project:


M0 Security & setup → M1 Data layer wiring → M2 Core pages →
M3 Secondary features → M4 Cross-cutting polish → M5 Integrations →
M6 Deployment prep

One module = one planning and audit checkpoint — not necessarily a hard session boundary. Build several related modules in the same session if you compact between them (Section 3, Rule 5). Only split across sessions when the session itself needs to reset. Within a session, still keep the work scoped to one module at a time — don't blend unrelated modules into the same prompt.


Audits — how often: at project kickoff (baseline), after every module, before any demo, and before deployment. Never skip this between modules — it's what catches drift before it compounds.


The Audit Loop:


1. Brain generates a short, read-only audit prompt
   (specific commands/checks — never "review everything")
2. You paste it into the execution tool
3. The tool runs it, returns a findings report
4. You paste that report back into the brain
5. Brain updates the Project Brief STATUS and generates the
   next fix prompt(s) — one at a time, priority order
6. Repeat from step 1 after fixes are applied

Audit prompt skeleton (Low effort, every time):


Run these checks. Report only — no fixes.
1. [specific grep/curl/command] → expected result
2. [specific grep/curl/command] → expected result
...
Report: ITEM / STATUS (OK / BROKEN / MISSING) / one-line detail.
End with: numbered priority list of what to fix.

